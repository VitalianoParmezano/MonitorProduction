**Monitor Production** (моніторинг виробництва) — внутрішня веб-система фіксації параметрів вимірювань та контролю якості продукції (ВТК) на виробничій лінії.

> Статус: етап планування архітектури. Розділи з позначкою 🚧 ще не остаточні.

## Можливості

- Оператор на робочому місці сканує штрихкод виробу, вводить результат вимірювання й відправляє його на сервер.
- Кожне робоче місце записує **один визначений параметр** у дані випробувань виробу.
- Бекенд перевіряє значення на допуски та допустимий діапазон.
- Адміністратор керує робочими місцями: яким шаблоном інтерфейсу вони користуються та який параметр вимірюють, і бачить превʼю інтерфейсу робочої станції.
- Вкладка моніторингу показує план/факт виробництва.
- Зберігаються фотографії виробів та технічна документація (datasheet).

## Архітектура

### Компоненти

Система модульна, контейнеризована (Docker Compose), складається з трьох сервісів:

| Сервіс | Технологія | Призначення |
| :--- | :--- | :--- |
| **db** | PostgreSQL 16 | Метадані виробів, результати замірів, налаштування робочих місць, посилання на файли |
| **nginx** | Nginx | Єдина точка входу (порт 80): віддає статику фронтенду та файли з `/uploads/`, проксує `/api/*` на бекенд |
| **backend** | Python, FastAPI | Бізнес-логіка, валідація допусків, запис у БД, безпечне збереження файлів, REST API |

Мережа внутрішня, тому HTTPS (порт 443) не використовується.

### Схема проходження трафіку

```
[ Клієнт / комп'ютер на виробничій лінії ]
           │
           │ HTTP (порт 80)
           ▼
     [ Nginx:80 ] ──────────────────────┐
      │         │                       │
      │         │ /api/* (проксі)       │ /uploads/*
      │         ▼                       ▼
      │    [ Backend:8000 ]    [ Директорія ./uploads/ ]
      │         │                       ▲
      │         │ запис метаданих       │ збереження файлів
      │         ▼                       │
      │    [ PostgreSQL:5432 ]          │
      │                                 │
      └───────> роздача статики (frontend/)
```

Шаблони інтерфейсу — це звичайні статичні файли з `frontend/`, їх віддає Nginx. Бекенд віддає лише дані (конфігурацію робочого місця, результати).

## База даних

PostgreSQL 16. Схема 🚧:

```
product_types 1 ──── N products 1 ──── N measurements

workstations (налаштування: який шаблон і який ключ результату у кожного місця)
```

### 1. Таблиця `product_types`

Довідник типів продукції. Усуває хаос на кшталт `Світильник` / `світильник` / `Світильники` і спрощує фільтрацію.

| Стовпець | Тип | Обмеження | Опис |
| :--- | :--- | :--- | :--- |
| `id` | `BIGSERIAL` | `PRIMARY KEY` | Ідентифікатор типу |
| `name` | `VARCHAR(64)` | `UNIQUE, NOT NULL` | Назва типу (`Світильник`, `Щит`) |

### 2. Таблиця `products`

Довідник моделей продукції.

| Стовпець | Тип | Обмеження | Опис |
| :--- | :--- | :--- | :--- |
| `id` | `BIGSERIAL` | `PRIMARY KEY` | Ідентифікатор моделі |
| `name` | `VARCHAR(255)` | `NOT NULL` | Назва виробу |
| `description` | `TEXT` | `NULL` | Розширений опис |
| `type_id` | `BIGINT` | `NOT NULL, FK → product_types(id)` | Тип продукції |
| `article` | `VARCHAR(100)` | `UNIQUE, NOT NULL` | Виробничий артикул (SKU) |
| `characteristics` | `JSONB` | `DEFAULT '{}'` | Номінальні характеристики та допуски |
| `datasheet_path` | `VARCHAR(512)` | `NULL` | Шлях до datasheet у `/uploads/datasheets/` |

### 3. Таблиця `workstations`

Робочі місця та їх налаштування. Керується з адмінки.

| Стовпець | Тип | Обмеження | Опис |
| :--- | :--- | :--- | :--- |
| `id` | `BIGSERIAL` | `PRIMARY KEY` | Ідентифікатор |
| `number` | `INT` | `UNIQUE, NOT NULL` | Номер робочого місця (його вводить оператор) |
| `name` | `VARCHAR(255)` | `NULL` | Назва / опис місця |
| `template` | `VARCHAR(64)` | `NOT NULL` | Назва шаблону без розширення (напр. `measurement`), відповідає запису в `templates.json` |
| `template_params` | `JSONB` | `DEFAULT '{}'` | Параметри шаблону (напр. `label`, `unit`) |
| `result_key` | `VARCHAR(64)` | `NULL` | Ключ у `q_tests_data`, який оновлює це місце (напр. `dielectric`) |

### 4. Таблиця `measurements`

Журнал проходження конкретного екземпляра виробу через робочі місця.

| Стовпець | Тип | Обмеження | Опис |
| :--- | :--- | :--- | :--- |
| `id` | `BIGSERIAL` | `PRIMARY KEY` | Ідентифікатор запису |
| `product_id` | `BIGINT` | `NOT NULL, FK → products(id)` | Модель виробу |
| `barcode` | `VARCHAR(128)` | `NOT NULL, UNIQUE` | Штрихкод / серійний номер екземпляра (один рядок на екземпляр) |
| `q_tests_data` | `JSONB` | `DEFAULT '{}'` | Результати випробувань (по ключу на робоче місце) |
| `stage_times` | `JSONB` | `DEFAULT '{}'` | Час сканування на кожному етапі |
| `notes` | `TEXT` | `NULL` | Примітки оператора, зокрема історія переробок |
| `photo_path` | `VARCHAR(512)` | `NULL` | Шлях до фото у `/uploads/photos/` |
| `release_date` | `DATE` | `NULL` | Дата випуску |
| `created_at` | `TIMESTAMPTZ` | `DEFAULT NOW()` | Час створення запису |

### Формат JSON-полів

**`q_tests_data`**: один ключ на робоче місце. Ключ задається в адмінці (`workstations.result_key`). Значення це обʼєкт із результатом, прапорцем придатності та номером місця.

```json
{
  "dielectric": {"value": 2500.0, "ok": true, "ws": 1},
  "final": {"value": "ok", "ok": true, "ws": 3}
}
```

**`stage_times`**: час запису на кожному етапі (ключ `ws<номер>`), ISO 8601 з часовим поясом. Кількість етапів може бути різною. Час ставить **сервер** (`now()` у БД), а не браузер.

```json
{
  "ws1": "2026-11-05T09:58:12.116680+02:00",
  "ws3": "2026-11-05T10:12:40.149380+02:00"
}
```

**Допуски** лежать у `products.characteristics` у ключі `limits` (по ключу результату):

```json
{
  "limits": {
    "dielectric": {"min": 100, "max": 5000, "range_min": 0, "range_max": 10000},
    "connection_test": {"expected": true},
    "network_type": {"allowed": ["zigbee", "matter"]}
  }
}
```

- `min` / `max` визначають, чи числове значення «в нормі» (`ok`). Обидва необовʼязкові.
- `range_min` / `range_max` це межі *правдоподібного вводу*: значення поза ними відхиляється з помилкою `422` і в журнал не потрапляє (захист від зайвого нуля при ручному вводі).
- `expected` — нечислове значення «в нормі», якщо `value == expected`.
- `allowed` — нечислове значення «в нормі», якщо `value` входить у список.
- Для нечислових результатів без `expected`/`allowed` прапорець `ok` надсилає сам шаблон. Якщо `expected` або `allowed` задано, **бекенд сам обчислює `ok`** і ігнорує `ok` від клієнта. Порівняння за типом: `true` не дорівнює `"true"`.

**Запис результату** робиться одним атомарним запитом, ключ передається як параметр, а не підставляється в текст SQL:

```sql
UPDATE measurements SET
    q_tests_data = q_tests_data || jsonb_build_object(%(key)s::text, %(entry)s::jsonb),
    stage_times  = stage_times  || jsonb_build_object(%(ws_key)s::text, to_jsonb(now())),
    notes = CASE WHEN %(note)s::text IS NULL THEN notes
                 ELSE concat_ws(E'\n', notes, %(note)s::text) END
WHERE barcode = %(barcode)s
```

Якщо штрихкоду немає в таблиці, оператор отримує помилку «Штрихкод не знайдено» (а не мовчазний порожній `UPDATE`).

**Створення виробу.** Якщо в `template_params` робочого місця задано `product_id`, то при першому скануванні виріб цієї моделі створюється автоматично (`INSERT ... ON CONFLICT DO NOTHING`, `release_date = CURRENT_DATE`). Зазвичай це перше місце на лінії. На інших місцях `product_id` не задають, і невідомий штрихкод дає помилку.

### Зв'язки та індекси

- `measurements.product_id → products.id`, `ON DELETE RESTRICT` (не можна видалити модель, якщо за нею є виміри).
- `products.type_id → product_types.id`, `ON DELETE RESTRICT`.
- `UNIQUE (measurements.barcode)`: миттєвий пошук виробу при скануванні та гарантія одного рядка на екземпляр.
- `btree (measurements.product_id)`: вибірки історії за моделлю.
- GIN-індекси на JSONB-полях **не створюються**: пошук ведеться за `barcode`, а GIN сповільнює запис. Додати, якщо з'явиться реальна потреба шукати всередині JSON.

### Історія та статус виробу

- Повторне вимірювання перезаписує значення ключа. Історія переробок фіксується в `notes`.
- Придатність виробу визначається за поточними даними у `q_tests_data`.

## Веб-інтерфейс

Фронтенд роздається Nginx на порту 80.

### Оболонка та шаблони

Інтерфейс оператора складається з **оболонки** та **шаблону**:

```
┌──────────────────────────────────────────┐
│ <header>  година · робоче місце · інфо   │  ← статично, малює оболонка
├──────────────────────────────────────────┤
│ <main id="content">                      │
│     тут розгортається шаблон             │  ← вантажиться за іменем
│ </main>                                  │
└──────────────────────────────────────────┘
```

Як це працює:

1. Оператор вводить номер робочого місця.
2. Оболонка викликає `GET /api/workstations/{number}/config` і отримує ім'я шаблону та його параметри.
3. Оболонка завантажує `templates/<ім'я>.html` у `#content` і викликає `init(root, config)` з `templates/<ім'я>.js`.

```js
async function loadTemplate(name, config) {
  const html = await fetch(`/templates/${name}.html`).then(r => r.text());
  content.innerHTML = html;
  const mod = await import(`/templates/${name}.js`);
  mod.init(content, config);
}
```

Правила для шаблонів:

- **Шаблон складається з двох файлів**: `.html` (фрагмент розмітки без `<html>`, `<head>`, `<body>`) і `.js` з функцією `init(root, config)`. Скрипти всередині `innerHTML` не виконуються, тому логіка живе окремо.
- **Назви за функцією, а не за номером місця** (`measurement`, `final-test`, `photo`), щоб вони жили довго. Перейменування файлу потребує оновлення `workstations.template` у БД.
- **Шаблон за видом інтерфейсу, а не за кожним параметром.** Опір ізоляції та опір заземлення відрізняються лише підписом, одиницями та допуском, тому це один шаблон `measurement` з параметрами `label`, `unit` у `template_params`. Окремий файл потрібен там, де інтерфейс справді інший (фінальний тест, фотофіксація).
- **Спільна логіка в `shared/`**: цикл «скан, ввід, відправити, очистити, фокус», блокування кнопки, сигнал успіху/помилки. У шаблоні лишається тільки те, чим він відрізняється.
- **Фокус на штрихкод** повертає оболонка: після завантаження шаблону та після кожної відправки фокус ставиться на елемент із маркером `data-scan`.
- **Очищення при зміні шаблону**: якщо шаблони перемикаються без перезавантаження сторінки, `init` має знімати обробники, повішені на `document` (наприклад, `keydown` для сканера). Якщо шаблон змінюється раз на вхід, достатньо перезавантажити сторінку.
- **Стилі шаблонів** обмежувати класами в межах `#content`, щоб вони не ламали оболонку.
- **Назву шаблону** підставляти в шлях лише після перевірки за списком з `templates.json` (щоб у `template` не потрапило щось на кшталт `../../x`).

**Маніфест `templates/templates.json`** описує доступні шаблони та їх параметри. Його читає адмінка (напряму як статику) для випадаючого списку шаблонів і форми параметрів:

```json
{
  "measurement": {
    "title": "Вимірювання параметра",
    "description": "Оператор сканує штрихкод і вводить число.",
    "params": {
      "label": {"type": "text", "title": "Підпис поля", "hint": "Текст біля поля значення"},
      "unit":  {"type": "text", "title": "Одиниці виміру"},
      "product_id": {"type": "model", "title": "Модель виробу (необовʼязково)"}
    }
  },
  "check": {
    "title": "Перевірка так/ні",
    "params": {
      "label": {"type": "text", "title": "Питання"},
      "yes_label": {"type": "text", "title": "Підпис кнопки «Так»"},
      "no_label": {"type": "text", "title": "Підпис кнопки «Ні»"},
      "product_id": {"type": "model", "title": "Модель виробу (необовʼязково)"}
    }
  },
  "final-test": {"title": "Фінальний тест", "params": {}},
  "photo":      {"title": "Фотофіксація",   "params": {}}
}
```

Новий шаблон це новий `.html` + `.js` + запис у маніфесті. Код адмінки чіпати не треба. Поле параметра може мати тип `text`, `number` або `model` (випадаючий список моделей замість голого ID) і необовʼязкову підказку `hint`, яку адмінка показує знаком питання при наведенні.

### Інтерфейс оператора

Цикл роботи на робочому місці:

1. Оператор скануює штрихкод, він підставляється в поле штрихкоду.
2. Вводить результат вимірювання вручну.
3. Натискає «Відправити».
4. Форма очищується, фокус повертається на поле штрихкоду.

Рекомендації до реалізації:
- кнопку «Відправити» блокувати на час запиту (захист від подвійного кліку);
- після відповіді показувати чіткий сигнал успіху або помилки та статус «в нормі / поза допуском»;
- сканер зазвичай надсилає Enter після коду, це можна використати для переходу в поле вимірювання;
- допустимий діапазон значення перевіряє бекенд (захист від зайвого нуля при ручному вводі).

### Адміністрування

Адмін-панель (з автентифікацією) дозволяє:
- задавати кількість робочих місць;
- вибирати для кожного місця шаблон та його параметри (форма будується за `templates.json`);
- задавати, який ключ `q_tests_data` оновлює кожне місце;
- керувати довідниками типів продукції та моделей;
- переглядати **превʼю робочої станції**.

**Превʼю.** Адмінка показує справжню оболонку в `<iframe>` і передає їй ім'я шаблону та конфіг через `postMessage`. Тому превʼю в точності збігається з тим, що побачить оператор, разом із шапкою.

```html
<iframe id="preview" src="/index.html?preview=1"></iframe>
```

```js
// адмінка: при будь-якій зміні полів форми
function updatePreview() {
  preview.contentWindow.postMessage({
    type: 'config',
    template: 'measurement',
    config: { label: 'Опір ізоляції', unit: 'МОм' }
  }, location.origin);
}
```

```js
// оболонка
const isPreview = new URLSearchParams(location.search).has('preview');

window.addEventListener('message', (e) => {
  if (!isPreview || e.origin !== location.origin || e.data.type !== 'config') return;
  loadTemplate(e.data.template, e.data.config);
});
```

Нюанси:
- у режимі `?preview=1` відправка вимкнена, щоб адмін не записав тестові дані в журнал;
- якщо в Nginx задається `X-Frame-Options`, значення має бути `SAMEORIGIN`, інакше iframe з власного сайту не відкриється;
- превʼю робити в розмірі реального екрану робочої станції та масштабувати через CSS `transform: scale()`, інакше розмітка виглядатиме інакше, ніж на справжньому моніторі.

### Моніторинг

Окрема вкладка (`/monitor/`) з показниками **план/факт** для кожного робочого місця. Дані оновлюються опитуванням `GET /api/monitor/summary` кожні 10 секунд.

- **План**: одне число на добу (`settings.daily_plan`), задається в адмінці.
- **Факт** робочого місця: кількість виробів, що пройшли це місце сьогодні (за міткою в `stage_times`; «сьогодні» рахується в часовому поясі `APP_TIMEZONE`).

Раз на пів години з-за віконця вибігає качечка і крякає. 🦆 Браузери блокують звук до першої взаємодії зі сторінкою, тому на моніторі один раз натисни «Увімкнути звук». Для перевірки натисни клавішу **D**.

## Бекенд та API

Бекенд на FastAPI. Інтерактивна документація: `/api/docs`.

| Метод | Шлях | Призначення |
| :--- | :--- | :--- |
| `GET` | `/api/workstations/{number}/config` | Шаблон, параметри та ключ результату для робочого місця |
| `POST` | `/api/measurements/submit` | Запис результату: `{workstation, barcode, value, ok?, note?}` |
| `POST` | `/api/measurements/photo` | Завантаження фото (`multipart`: `workstation`, `barcode`, `file`) |
| `GET` | `/api/units/{barcode}` | Поточний стан виробу (для фінального тесту) |
| `GET` | `/api/monitor/summary` | План/факт для моніторингу |
| `*` | `/api/admin/...` | CRUD типів, моделей, робочих місць, план; datasheet. HTTP Basic |

Коди помилок: `404` невідомі робоче місце або штрихкод, `422` значення поза допустимим діапазоном вводу, `409` порушення унікальності або звʼязків, `413` завеликий файл.

Валідація: числові значення з лімітами перевіряє бекенд; тип файлу визначається за вмістом (JPEG/PNG/WebP для фото, PDF для datasheet), а не за іменем; імена файлів генеруються (UUID); `template` у робочому місці має відповідати `^[a-z0-9-]+$`.

## Сховище файлів

Директорія `uploads/` на хості монтується у контейнери:

| Директорія | Вміст | Прив'язка |
| :--- | :--- | :--- |
| `uploads/photos/` | Фото виробів | `measurements.photo_path` |
| `uploads/datasheets/` | Технічна документація | `products.datasheet_path` |

Правила:
- імена файлів генеруються бекендом (UUID), оригінальні імена не використовуються;
- бекенд перевіряє тип і розмір файлу, у Nginx задається `client_max_body_size`;
- у контейнері Nginx том змонтовано лише для читання (`ro`).

## Розгортання

Потрібні Docker та Docker Compose.

```bash
git clone <repo> factory-system
cd factory-system
cp .env.example .env     # заповнити паролі БД та адмінки
docker compose up -d --build
```

Після запуску:

| Адреса | Що |
| :--- | :--- |
| `http://<хост>/` | Інтерфейс оператора (вхід за номером робочого місця) |
| `http://<хост>/monitor/` | Моніторинг |
| `http://<хост>/admin/` | Адміністрування (логін і пароль з `.env`) |
| `http://<хост>/api/docs` | Документація API |

Примітки:
- Демо-дані (`db/init/02_seed_demo.sql`) створюють кілька тестових записів. Для промислового запуску видали цей файл **до першого старту** (SQL з `db/init/` виконується лише на порожньому `pgdata`).
- Для подальших змін схеми потрібні міграції (наприклад, Alembic).
- Бекапити `pgdata/` та `uploads/` слід узгоджено.
- Паролі в `.env` без спецсимволів `@ : / # %` (пароль БД входить у `DATABASE_URL`).

## Відкриті питання

Прийнято в коді, але варто переглянути:
- **Допуски** лежать у `products.characteristics.limits`. Якщо їх буде багато, винести в окрему структуру на рівні типу продукції.
- **Створення виробу** робить місце з `product_id` у параметрах. Альтернатива: окремий крок реєстрації.
- **План** один на добу для всіх місць (`settings.daily_plan`). Якщо потрібен план за моделями чи змінами, потрібна окрема таблиця.
- **Факт** це кількість виробів, що пройшли кожне місце сьогодні. Якщо «факт» має означати лише готові вироби, треба визначити, яке місце останнє.
- **Бекенд не перевіряє**, що `workstations.template` є в `templates.json` (лише формат імені). Перевірка потребує монтування `frontend/templates` у бекенд як `ro`.

Ще не вирішено:
- Де зберігається список обовʼязкових ключів для визначення загальної придатності виробу (напр. `product_types.required_keys`).
- Єдина назва проєкту: `Monitor Production` чи `factory-system`.
- Чи потрібне оновлення моніторингу в реальному часі (зараз опитування кожні 10 с).
