## Контекст проєкту

Monitor Production: внутрішня веб-система ВТК на виробничій лінії. Стек: Nginx + FastAPI (psycopg3, без ORM) + PostgreSQL 16, docker compose. Фронтенд без збірки: чистий HTML/JS (ES modules), Nginx роздає `frontend/` як статику. Документація в `README.md` (українською).

Як це влаштовано:

- Таблиця `workstations`: `number`, `name`, `template` (ім'я шаблону без розширення), `template_params` (JSONB), `result_key` (ключ у `q_tests_data`, який оновлює це місце).
- Таблиця `measurements`: один рядок на виріб (`barcode UNIQUE`), `q_tests_data` JSONB, `stage_times` JSONB, `notes`, `photo_path`.
- Запис результату: `POST /api/measurements/submit` з тілом `{workstation, barcode, value, ok?, note?}` (`backend/app/routers/public.py`). Значення зберігається як `q_tests_data[result_key] = {"value": ..., "ok": bool, "ws": number}`. Числові значення з лімітами оцінює функція `_evaluate`, для нечислових вона довіряє `ok` з клієнта.
- Допуски лежать у `products.characteristics.limits[result_key]`: `min`, `max` (для «в нормі»), `range_min`, `range_max` (відсікають помилки вводу, відповідь 422).
- Фронтенд: оболонка `frontend/index.html` + `frontend/shared/shell.js` завантажує `frontend/templates/<ім'я>.html` (фрагмент розмітки) у `#content` і викликає `init(root, cfg)` з `<ім'я>.js` (може повернути функцію очищення). `cfg = {workstation, params, name, preview}`.
- Маніфест `frontend/templates/templates.json` описує доступні шаблони та їхні параметри. З нього адмінка будує випадаючий список шаблонів і поля форми, а також превʼю (iframe з оболонкою + postMessage).
- Спільні модулі: `frontend/shared/api.js`, `ui.js` (showResult, beep, focusScan), `style.css`.

## Проблема

1. Єдиний шаблон для вимірювань, `measurement`, приймає лише **число**: `measurement.js` робить `Number(...)` і відхиляє решту повідомленням «Введіть число». Тому не можна налаштувати робоче місце з перевіркою типу **«Є звʼязок із сервером? так/ні»**. В адмінці таке місце створюється (підпис поля задати можна), а оператор на ньому нічого не збереже.
2. Бекенд оцінює придатність лише для чисел із `limits`. Для нечислових значень (так/ні, вибір зі списку) він бездумно довіряє прапорцю `ok` від клієнта, а правила «що вважається нормою» для моделі задати нема де.
3. У `products.characteristics` зберігаються й нечислові дані (приклад: `{"network_type": ["zigbee", "matter"], "connection_test": true}`), але система їх ніяк не використовує. Це свідома межа поточного завдання: див. «Чого не робити».

## Бажаний результат

**A. Шаблон `check` («Перевірка так/ні»)**

Файли `frontend/templates/check.html`, `check.js` і запис у `templates.json`. Якщо вони вже існують у репозиторії, перевір їх на відповідність цьому опису й доведи до нього.

- Поле штрихкоду (`data-scan`). Після Enter від сканера фокус переходить на першу кнопку відповіді.
- Питання з `params.label` (за замовчуванням «Перевірка пройдена?») і дві великі кнопки: «Так» і «Ні». Підписи беруться з `params.yes_label` і `params.no_label`.
- Відправка на `/api/measurements/submit`: `value: true|false`, `ok` дорівнює тому самому значенню. «Так» означає «в нормі», «Ні» означає «поза нормою».
- Порожній штрихкод: помилка «Проскануйте штрихкод» без запиту. Кнопки блокуються на час запиту (захист від подвійного кліку). Після успіху: зелена або червона смуга результату, звуковий сигнал (`beep`), очищення поля, фокус на штрихкод. При помилці: червона смуга, поле штрихкоду виділене, значення не очищається.
- У режимі превʼю (`cfg.preview`) відправка вимкнена, показується повідомлення «Режим превʼю».
- Параметри в маніфесті: `label`, `yes_label`, `no_label`, `product_id` (останній працює так само, як у шаблона `measurement`).

**B. Бекенд: правило норми для нечислових результатів**

У функції `_evaluate` (`backend/app/routers/public.py`) додай підтримку в `products.characteristics.limits[result_key]`:

- `"expected": <значення>`: результат у нормі, якщо `value == expected`;
- `"allowed": [<значення>, ...]`: результат у нормі, якщо `value` входить у список.

Якщо одне з цих правил задано, **бекенд сам обчислює `ok`** і ігнорує `ok` від клієнта. Якщо ні, поведінка лишається такою, як зараз (клієнт надсилає `ok`). Числова логіка (`min`, `max`, `range_min`, `range_max`) не змінюється. Порівнювати треба за типом: `true` не дорівнює `"true"`.

Приклад характеристик моделі:

```json
{
  "limits": {
    "connection_test": {"expected": true},
    "network_type": {"allowed": ["zigbee", "matter"]}
  }
}
```

## Обмеження

- Без нових залежностей, без збірки фронтенду, без змін схеми БД.
- Не ламати поточний контракт API та вже збережені дані.
- SQL лише з параметрами (без підстановки в текст запиту). Текст у DOM лише через `textContent`, не `innerHTML`.
- Інтерфейс українською, стиль коду як у сусідніх файлах.

## Чого не робити без окремого уточнення

Автоматично показувати чи ховати робочі місця залежно від полів характеристик моделі (наприклад, `connection_test: true`) і будь-яку іншу логіку на основі `characteristics`, крім `limits`. Якщо вважаєш, що це потрібно для вирішення, не реалізуй, а запропонуй окремо.

## Перевірка

Підніми стек (`docker compose up -d --build`) і перевір:

1. Через адмінку створи робоче місце з шаблоном «Перевірка так/ні» і `result_key = connection_test`. Превʼю має показати питання та дві кнопки.
2. Модель із `limits.connection_test.expected = true`: відправ «Так», у `q_tests_data` має зʼявитись `{"value": true, "ok": true, "ws": N}`. Відправ «Ні», має бути `ok: false`.
3. Через curl: `POST /api/measurements/submit` з `{"workstation": N, "barcode": "...", "value": false, "ok": true}` при заданому `expected: true` має зберегти `ok: false` (бекенд має пріоритет).
4. Для моделі **без** `expected`/`allowed` результат береться з клієнтського `ok`, як раніше.
5. Числове вимірювання на шаблоні `measurement` з `limits.min/max` працює без змін.
6. Невідомий штрихкод дає «Штрихкод не знайдено», а не мовчазний успіх.

У відповіді коротко опиши, що змінено по файлах, і окремо напиши, що з перевірок ти виконав, а що ні.
