# TECHNICAL_DEBT — Monitor Production

Проблеми згруповані за серйозністю. Позначки: 🔴 критично, 🟡 середньо, 🟢 дрібно.
Всі пункти — факти з коду/файлів; припущення позначені окремо.

## 🔴 Критично

1. **Немає жодних автоматизованих тестів.**
   У репозиторії немає `pytest`/`unittest`/`vitest`/`jest`, CI та тестових файлів. Логіка допусків
   (`_evaluate`), SQL-оновлення, валідація форм — усе без регресійного покриття.

2. **Немає міграцій БД.**
   Схема лише в `db/init/*.sql`, які виконуються тільки на порожньому `pgdata`. Будь-яка зміна схеми
   на живій базі потребує ручної міграції або перестворення тома (втрата даних). README саме пропонує Alembic.

3. **Демо-дані можуть потрапити в продакшен.**
   `db/init/02_seed_demo.sql` створює тестові типи/модель/місця при першій ініціалізації БД.
   Захисту від цього в коді немає — лише застереження в README.

4. **Секрети/сторонні файли в робочій директорії.**
   `secret/deepseek_api` (37 байт, ймовірно API-ключ) і `secret/factory-system.zip`. Каталог `secret/`
   в `.gitignore`, тож у Git вони не потрапляють, але лежать поруч із кодом. Призначення `deepseek_api`
   невідоме (у коді `deepseek` не використовується).

## 🟡 Середньо

5. **Публічні API без авторизації та без захисту від зловживань.**
   `POST /api/measurements/submit`, `POST /api/measurements/photo` та інші публічні маршрути не мають
   auth/CSRF/rate-limit. Це свідоме рішення «внутрішня мережа», але варто зафіксувати як ризик.

6. **Фото виробів не мають UI перегляду.**
   Фото зберігається (`photo_path`), але ніде не відображається (`final-test` показує лише `q_tests_data`).

7. **Дублювання SQL вибірки робочого місця.**
   `public.py`: `_workstation()` і ендпоінт `workstation_config` виконують ідентичний `SELECT` робочого
   місця. Мінорне, але ризик розсинхрону при змінах.

8. **`settings` як generic key-value з JSONB-значенням.**
   План зберігається як JSONB-число (`Jsonb(int)`), читається через `int(row["value"])`. Працює, але
   крихко (немає типізації; ключ `daily_plan` «магічний»).

9. **Семантика «факт» у моніторингу.**
   `fact` = кількість рядків `measurements` з ключем `ws<номер>` у `stage_times` за сьогодні. Повторне
   сканування того самого виробу не збільшує факт; незавершені вироби теж рахуються як факт місця.
   Питання «що вважати готовим» — відкрите (див. README).

10. **Сироти-файли при видаленні/заміні.**
    При заміні datasheet чи видаленні моделі/виробу старі файли в `uploads/` не видаляються.

11. **Бекенд не валідує існування `workstations.template`.**
    Перевіряється лише формат імені (`^[a-z0-9-]+$`), а не наявність у `templates.json`. Помилка в назві
    проявиться лише на операторському екрані (fetch 404).

12. **Відсутня пагінація/пошук у адмін-списках.**
    `GET /api/admin/products`, `/workstations`, `/product-types` повертають усі рядки. На малих обсягах
    ок, але не масштабується.

## 🟢 Дрібно

13. **Застарілий статус у README.** Рядок «етап планування архітектури» не відповідає реалізації.
    Також розбіжність назв проєкту (`MonitorProduction` vs `factory-system/`).

14. **`bugs.md` — незакритий пункт і не в Git.** Файл не відстежується (`??` у `git status`) і містить
    ще одне завдання: «Додати „скрити превʼю“ і воно стає неактивним за матовим склом».

15. **`_evaluate` неявна логіка.** Для числа без `limits` функція повертає `True` завжди; для нечислових
    довіряє `client_ok`. Код коректний, але потребує коментаря/тесту, щоб не зламати при рефакторингу.

16. **Timezone передається в опцію зʼєднання БД рядком** (`f"-c timezone={TIMEZONE}"`). Малоймовірна,
    але теоретична можливість інʼєкції через `.env` (внутрішня мережа).

17. **Превʼю повністю `inert`.** Це виправлення бага з фокусом, але означає, що в превʼю не можна
    взаємодіяти навіть для перевірки (напр. перевірити Enter-перехід). Прийнятно, але свідомо обмежує.

## Припущення / не перевірено

- Твердження про відсутність тестів і CI зроблено за вмістом репозиторію; конфігурацію CI поза
  репозиторієм (напр. у GitHub Actions окремо) перевірити неможливо.
