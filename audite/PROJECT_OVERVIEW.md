# PROJECT_OVERVIEW — Monitor Production

## Що це

**Monitor Production** — внутрішня веб-система фіксації параметрів вимірювань і контролю якості
продукції (ВТК) на виробничій лінії. Оператор на робочому місці сканує штрихкод виробу,
вводить/фіксує результат, сервер перевіряє значення на допуски й записує його в журнал.
Адміністратор керує довідниками та робочими місцями, а окрема вкладка показує план/факт виробництва.

## Статус

- Код **реалізований і працює** як єдиний контейнеризований застосунок (Docker Compose).
- У `README.md` перший рядок ще каже «етап планування архітектури» — це **застаріла позначка**,
  яка не відповідає фактичному стану коду (повний бекенд + фронтенд + nginx + БД + демо-дані).
- Git: гілки `master` (початковий README) і `dev` (робоча, останній коміт — виправлення фокуса
  в превʼю адмінки). Робоча директорія називається `MonitorProduction`, але в README корінь
  згадується як `factory-system/` — розбіжність у назві проєкту.

## Технологічний стек

| Шар | Технологія |
| :--- | :--- |
| Frontend | Vanilla JavaScript (ES-модулі), HTML5, CSS3. Без фреймворків, без збірки, без `package.json` |
| Backend | Python 3.12 (Docker `python:3.12-slim`), FastAPI, Uvicorn, psycopg 3 (async + pool), python-multipart, Pydantic |
| База даних | PostgreSQL 16 |

| Оркестрація | Docker Compose (3 сервіси: `db`, `backend`, `nginx`) |
| Автентифікація | HTTP Basic тільки для адмінки; робочі місця — без авторизації (внутрішня мережа) |
| Транспорт | HTTP (порт 80), HTTPS не використовується |

## Можливості

### Реалізовано повністю

- Вхід оператора за номером робочого місця, завантаження шаблону інтерфейсу за конфігом.
- Три шаблони робочих місць: `measurement` (числове вимірювання), `photo` (фотофіксація),
  `final-test` (фінальний вердикт із переглядом історії виробу).
- Запис результату в `q_tests_data` з перевіркою допусків (`min/max`) і діапазону вводу
  (`range_min/range_max`) на бекенді.
- Автостворення виробу при першому скануванні (якщо в параметрах місця задано `product_id`).
- Завантаження фото виробів (JPEG/PNG/WebP) і datasheet (PDF) з перевіркою типу за вмістом файлу.
- Адмінка: CRUD типів продукції, моделей (з datasheet-посиланням «PDF»), робочих місць,
  добового плану, превʼю робочої станції через iframe + `postMessage`.
- Моніторинг: план/факт по кожному робочому місцю, оновлення опитуванням кожні 10 с.
- Генерація UUID-імен файлів, обмеження розміру (10 МБ фото / 30 МБ datasheet).

### Реалізовано частково

- **Фото виробів** — завантажуються і зберігаються, але **немає UI для їх перегляду**
  (шлях `photo_path` повертається в `GET /api/units/{barcode}`, але шаблон `final-test` його не показує).
- **Загальна придатність виробу** — визначається за поточними даними в `q_tests_data`, але
  списку «обовʼязкових ключів» для підсумкової придатності в коді немає (див. відкриті питання README).

### Відсутнє

- Автоматизовані тести (жодного тесту: немає `pytest`, `unittest`, `vitest`/`jest`, CI).
- Міграції схеми БД (тільки init-скрипти, які виконуються на порожньому `pgdata`).
- Пагінація, пошук, фільтри в адмін-списках.
- Реальний час у моніторингу (лише опитування).
- Розмежування ролей адміністраторів, сесії, CSRF-захист (мережа внутрішня — свідомо спрощено).

## Запуск проєкту

Інструкція з README:

```bash
git clone <repo> factory-system
cd factory-system
cp .env.example .env      # заповнити паролі БД та адмінки
docker compose up -d --build
```

Після запуску:

| Адреса | Що |
| :--- | :--- |
| `http://<хост>/` | Інтерфейс оператора |
| `http://<хост>/monitor/` | Моніторинг |
| `http://<хост>/admin/` | Адміністрування (HTTP Basic) |
| `http://<хост>/api/docs` | Документація API |

**Стан у цій робочій директорії (перевірено):**
- Docker (29.0.1) і Docker Compose (v2.40.3) **доступні**.
- Файл `.env` **відсутній**, каталог `pgdata` **відсутній** → БД ще не ініціалізована,
  застосунок **не запускався** в цьому середовищі. Запуск **не перевірено**.
- `uploads/` містить лише `.gitignore`; підкаталоги `photos/` і `datasheets/` створює бекенд на старті.

## Практичні сценарії

### Як влаштований план

- План — це **одне число на добу для всіх місць**: `settings.daily_plan` (таблиця `settings`,
  ключ `daily_plan`, значення зберігається як JSONB-число).
- Задається в адмінці на вкладці «План» → `PUT /api/admin/settings` з `{ "daily_plan": N }`.
- «Факт» робочого місця — кількість виробів, у яких у `measurements.stage_times` є ключ
  `ws<номер>` з часом **сьогодні** (у часовому поясі `APP_TIMEZONE`; час ставить БД через `now()`).
- Моніторинг раз на 10 с читає `GET /api/monitor/summary` → `{ plan, workstations: [{ number, name, fact }] }`
  і малює картки з відсотком виконання.
- Важлива семантика: повторне сканування того самого виробу на тому самому місці **не збільшує**
  факт (рахується рядок `measurements`, а не кількість сканувань).

### Як додати новий товар (модель продукції)

1. Переконатися, що є потрібний тип: адмінка → «Типи продукції» → додати (`POST /api/admin/product-types`).
2. Адмінка → «Моделі» → «Нова модель» (`POST /api/admin/products`). Обовʼязкові поля:
   - `name` — назва;
   - `article` — артикул (має бути унікальним);
   - `type_id` — тип продукції;
   - `characteristics` — JSON, зазвичай із допусками:
     ```json
     { "limits": { "dielectric": { "min": 100, "max": 5000, "range_min": 0, "range_max": 10000 } } }
     ```
     Ключ у `limits` має збігатися з `result_key` робочого місця.
3. Опційно: завантажити datasheet (PDF) через кнопку «Завантажити datasheet (PDF)».

### Як додати нову панель (шаблон) робочої станції

Шаблон = пара файлів + запис у маніфесті. Код адмінки міняти **не треба**.

1. Створити розмітку `frontend/templates/<name>.html` — фрагмент **без** `<html>/<head>/<body>`.
   Поле штрихкоду позначати `data-scan`, блок результату — `data-result`.
2. Створити логіку `frontend/templates/<name>.js`:
   ```js
   export function init(root, cfg) {
     // cfg = { workstation, params, preview, name }
   }
   ```
   Обовʼязково перевіряти `cfg.preview` і не надсилати дані в режимі превʼю.
3. Додати запис у `frontend/templates/templates.json`:
   ```json
   { "my-panel": { "title": "Моя панель", "params": { "some": { "type": "text", "title": "Підпис" } } } }
   ```
   Це дасть адмінці випадаючий пункт і форму параметрів автоматично.
4. В адмінці → «Робочі місця» → «Нове робоче місце»:
   - вибрати шаблон `<name>`;
   - задати параметри (вони потраплять у `workstations.template_params`);
   - задати `result_key` (ключ у `q_tests_data`, який оновлює місце).
5. Для числового вимірювання вказати допуски в `products.characteristics.limits` за цим самим `result_key`.

  архів-знімок проєкту; вміст **не розпаковувався**.
