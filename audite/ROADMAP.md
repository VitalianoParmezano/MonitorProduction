# ROADMAP — Monitor Production

Рекомендований порядок робіт. Етапи можна виконувати паралельно, але P0 — перед будь-яким
розширенням функціональності. Пункти співвіднесені з `TECHNICAL_DEBT.md`.

## P0 — Стабілізація та безпека (перед продовженням розробки)

1. **Автоматизовані тести** (TD-1):
   - бекенд: `pytest` + `httpx` для маршрутів і окремо unit-тест `_evaluate` (допуски, діапазон, бульові);
   - фронтенд: мінімальні перевірки `shared/ui.js` і логіки шаблонів (за потреби Vitest);
   - CI (напр. GitHub Actions): збірка образу + тести на кожен PR.
2. **Міграції БД** (TD-2): підключити Alembic, перенести схему з `db/init/01_schema.sql` як baseline,
   далі — лише міграції.
3. **Відокремити демо-дані** (TD-3): не класти `02_seed_demo.sql` в автоматичний `initdb`, а зробити
   окрему команду/компос-профіль для демо.
4. **Прибрати сторонні файли** (TD-4): вирішити долю `secret/deepseek_api` і `secret/factory-system.zip`
   (видалити або задокументувати; ключ не використовується в коді).

## P1 — Надійність і завершеність

5. **Перегляд фото виробів** (TD-6): показати `photo_path` у `final-test` (і/або в адмінці — картка виробу).
6. **Очищення сиріт-файлів** (TD-10): видаляти старий datasheet/фото при заміні та при видаленні записів.
7. **Валідація шаблону на бекенді** (TD-11): звіряти `workstations.template` з `templates.json`
   (потребує монтування `frontend/templates` у backend як `ro`).
8. **Пагінація/пошук в адмін-списках** (TD-12): `limit/offset` + поле пошуку для моделей/типів/місць.
9. **Закрити `bugs.md`**: реалізувати кнопку «Сховати превʼю» з матовим склом (другий пункт у файлі),
   після чого видалити/перевести файл у трекер.

## P2 — Функціональність (бізнес-вимоги)

10. **План за моделями/змінами** (див. відкриті питання README): замість одного `daily_plan` на всі місця —
    таблиця планів (місце × дата × кількість). Уточнити вимоги в замовника.
11. **Підсумкова придатність виробу**: визначити список обовʼязкових ключів (напр. `product_types.required_keys`)
    і підрахунок «придатний, якщо всі обовʼязкові ключі `ok:true`».
12. **Чітка семантика «факт»**: визначити останнє місце (готовий виріб) або рахувати факт інакше
    (напр. унікальні вироби, що завершили всі етапи).
13. **Опційно — реальний час моніторингу**: SSE/WebSocket замість опитування кожні 10 с.

## P3 — Гігієна та досвід розробника

14. **Актуалізувати README** (TD-13): прибрати «етап планування», узгодити назву проєкту.
15. **Додати лінтери/форматери** (ruff для Python, ESLint/Prettier для JS) та pre-commit.
16. **Типізувати `settings`**: окрема колонка/таблиця для плану замість generic JSONB key-value.
17. **Документація API-прикладів**: додати приклади запитів у `/api/docs` (description) для операторів.

## Припущення / не перевірено

- Пріоритети P1/P2 залежать від бізнес-вимог (чи потрібен план за моделями, як рахувати «готовий» виріб).
  Точки 10–12 потребують уточнення у замовника; порядок умовний.
