## 1. План/факт → «Партії»

### Як є зараз
- План — **одне число на добу для всіх місць**: `settings.daily_plan`
  (`backend/app/routers/admin.py`, `SettingsIn.daily_plan`).
- Факт місця — кількість рядків `measurements`, у яких `stage_times` містить ключ
  `ws<номер>` з часом сьогодні (`backend/app/routers/monitor.py`).
- Жодного поняття «партія/зміна/продукт» у плані немає: план не привʼязаний ні до
  продукту, ні до часу, ні до конкретних місць.

### Що хочеться (з Task.md)
- Кнопка «Почати партію» в адмінці; у партії вказується план/факт.
- Усі робочі зони «пересуваються» на цей план/факт.
- Якщо під час партії треба доробити інший продукт — система автоматично підтягує
  ту партію.

### Рекомендована модель даних
Нова таблиця партій + привʼязка виміру до партії:

```sql
CREATE TABLE batches (
    id         BIGSERIAL PRIMARY KEY,
    code       VARCHAR(64) NOT NULL,          -- людська назва, напр. "Партія #12"
    product_id BIGINT REFERENCES products(id) ON DELETE RESTRICT, -- яку модель робимо
    plan       INT NOT NULL DEFAULT 0 CHECK (plan >= 0),
    opened_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    closed_at  TIMESTAMPTZ                     -- NULL = партія активна
);

ALTER TABLE measurements ADD COLUMN batch_id BIGINT
    REFERENCES batches(id) ON DELETE SET NULL;
```

> ⚠️ Схема в цьому проєкті застосовується лише на порожньому `pgdata` (init-скрипти).
> Для живої бази треба або перестворити том, або (правильно) завести Alembic-міграції —
> це вже є в `ROADMAP.md` (пункт TD-2). Тому партії логічно робити разом із міграціями.

### Правило «автопідтягування» партії
Під час `POST /api/measurements/submit` виріб уже знаходиться/створюється
(`_ensure_unit`). Далі визначаємо партію:
1. Є активна партія (без `closed_at`) з тим самим `product_id`, що й у виробу →
   приписуємо вимір до неї. **Це і є «система автоматично підтягує ту партію»** —
   відсканували інший продукт → він сам потрапив у свою партію.
2. Інакше — до останньої відкритої партії (поточна «за замовчуванням»).
3. Якщо активних партій немає — вимір без партії (факт рахується за сьогодні, як раніше).

Практично це означає: в `_ensure_unit` повертаємо `product_id`, а в `submit` одним
запитом шукаємо потрібну партію і дописуємо `batch_id` в `UPDATE measurements`.

### API (нові ендпоінти в `routers/admin.py`, HTTP Basic)
- `GET /api/admin/batches` — список партій (всі або лише активні).
- `POST /api/admin/batches` — «Почати партію»: `{ code?, product_id, plan }` →
  створює активну партію.
- `POST /api/admin/batches/{id}/close` — завершити партію (ставить `closed_at`).
- `DELETE /api/admin/batches/{id}` — видалити порожню/помилкову партію.

### Моніторинг (`routers/monitor.py`)
`GET /api/monitor/summary` тепер повертає активні партії, а не одне число:

```json
{
  "batches": [
    { "id": 3, "code": "Партія #12", "product": "LED-40", "plan": 100,
      "workstations": [ { "number": 1, "name": "Вимірювання", "fact": 87 } ] }
  ]
}
```

Факт місця рахуємо так само (ключ `ws<номер>` у `stage_times` за сьогодні), але з
додатковим фільтром `m.batch_id = <партія>` (або `batch_id IS NULL` для позапартійних).

### Відкриті питання (це і просили «обговорити»)
1. **Що вважати «фактом» партії**: пройшли це місце (поточна семантика) чи **готові**
   вироби (пройшли останнє місце)? Рекомендую залишити поточну семантику (факт місця),
   а «готовий» рахувати окремим показником за останнім місцем.
2. **Чи можна кілька активних партій одночасно?** Модель вище це підтримує
   (завдяки привʼязці до `product_id`). Якщо партія завжди одна — спростіть до одного
   «активного» запису в `settings`.
3. **План привʼязаний до продукту** (`batches.product_id`) — чи потрібен ще план
   «за місцями»? Якщо так, додайте таблицю `batch_plan(ws_number, plan)`.
4. Чи треба історію партій з архівом факту на момент закриття (щоб бачити, скільки
   зробили в кожній зміні)? Раджу зберігати `closed_at` і рахувати факт по
   `batch_id` — це вже дає історію без окремого архіву.

## 2. Адмін-панель: зрозуміла форма робочих місць

### Що незрозуміло (і що це насправді)
Форма робочого місця (`frontend/admin/index.html` + `admin.js`) зараз має поля:

| Поле | Що це насправді |
| :--- | :--- |
| Номер | номер робочого місця, який вводить оператор на вході (`workstations.number`) |
| Назва | людська назва місця (показується в шапці та на моніторингу) |
| Шаблон | яку «панель» показувати оператору: `measurement` (число), `photo` (фото), `final-test` (вердикт) |
| Параметри шаблону | налаштування конкретної панелі, будуються автоматично з `frontend/templates/templates.json` |
| **Створювати виріб моделі з ID** | це параметр `product_id` у `templates.json`. Якщо задано — при першому скануванні штрихкода система **сама створює** рядок виробу в `measurements` (`_ensure_unit` у `public.py`). Це **ID моделі** (число з таблиці `products`), а не «дата» |
| **Ключ результату в q_tests_data** | `workstations.result_key` — ключ у JSONB-обʼєкті `measurements.q_tests_data`, який оновлює це місце (напр. `dielectric`). Цей самий ключ має бути в допусках моделі `characteristics.limits` |

> Щодо «текст/дата»: у формі є текстові поля параметрів (`label` — підпис поля,
> `unit` — одиниці) і числове `product_id`. «Дата» як така оператором не вводиться —
> `release_date` (дата випуску) підставляється автоматично (`CURRENT_DATE`) при
> створенні виробу. Тобто «дата» — це не поле форми, а службове значення в БД.

### Рішення: переписати форму + підказки
1. **Замінити число `product_id` на випадаючий список моделей.** У `templates.json`
   додати новий тип поля `"model"`; адмінка (`admin.js::renderParams`) для такого типу
   малює `<select>` із `GET /api/admin/products` (назва + артикул замість голого ID).
2. **Додати підказки (ⓘ при наведенні).** У `templates.json` до кожного параметра
   додати `"hint"`, а в `admin.js` обгорнути підпис у `<label title="...">` або
   окремий елемент-тултіп. Це дає підказку без зміни бекенду.
3. **Перейменувати незрозумілі написи** на людську мову:
   - `result_key` → «Назва параметра (куди записується результат)» з підказкою
     «Має збігатися з ключем у допусках моделі, напр. `dielectric`».
   - `product_id` → «Модель виробу (необовʼязково)» з підказкою «Якщо обрати модель,
     при першому скануванні нового штрихкода виріб створюється автоматично».
4. **Згрупувати форму в кроки** (1. Що за місце → 2. Яка панель → 3. Параметри →
   4. Куди писати результат), щоб будь-хто розумів послідовність.
5. **Дописати короткий опис кожного шаблону** (`"description"` у `templates.json`),
   який показується під випадаючим списком «Шаблон».

Приклад оновленого `templates.json`:

```json
{
  "measurement": {
    "title": "Вимірювання параметра",
    "description": "Оператор сканує штрихкод і вводить число. Бекенд перевіряє допуски.",
    "params": {
      "label": { "type": "text", "title": "Підпис поля", "hint": "Текст біля поля значення, напр. «Опір ізоляції»" },
      "unit":  { "type": "text", "title": "Одиниці виміру", "hint": "Напр. кВ, Ом, мм" },
      "product_id": { "type": "model", "title": "Модель виробу (необовʼязково)", "hint": "Якщо обрати — виріб створюється автоматично при першому скануванні" }
    }
  }
}
```

Зміни лише у фронтенді (`templates.json`, `admin.js`, `admin.css`, `index.html`) —
бекенд чіпати не треба.

## 3. «А якщо значення не цифра?» + зручне налаштування допусків

### Звідки беруться типи значень
`POST /api/measurements/submit` приймає `value: bool | float | str`
(`routers/public.py`, клас `SubmitIn`):
- `measurement` (шаблон) шле **число** (`float`) — `measurement.js`.
- `final-test` шле **бульове** рішення «придатний/непридатний» (`value: "ok"/"nok"`,
  `ok: true/false`) — `final-test.js`.
- `photo` взагалі не шле `value` (окремий `POST /measurements/photo`).

Допуски зберігаються в `products.characteristics.limits[result_key]`:

```json
{ "limits": { "dielectric": { "min": 100, "max": 5000, "range_min": 0, "range_max": 10000 } } }
```

Логіка перевірки — `_evaluate()`:
- `range_min/range_max` — «відсічка помилок вводу»: значення поза цим діапазоном
  повертає **422** (напр. оператор ввів 10⁹ замість 1000).
- `min/max` — допуск: значення в межах → `ok: true` (зелене), поза → `ok: false`.
- **Якщо значення не число** — бекенд не вміє порівнювати з `min/max` і просто
  довіряє прапорцю `ok`, який прислав шаблон (`client_ok`). Тому `final-test`
  працює коректно, а от «текстове» значення з авто-перевіркою зараз не підтримується.

### Що зробити
1. **Замінити JSON-`characteristics` у адмінці на структуровану форму** (зараз це
   «голий» textarea в `admin.js::product-form`). Зробити «білдер допусків»:
   - кнопка «Додати параметр» → вводиш ключ (той самий `result_key`), тип значення
     (число / текст / вибір / так-ні), потім поля `min`, `max`, `range_min`,
     `range_max` — **звичайні number-поля + повзунки (range)**.
   - адмінка збирає це назад у JSON і шле у `characteristics` — бекенд не міняється.
2. **Для нецифрових значень** розширити схему допусків (опційно):
   - `{ "type": "choice", "options": ["A", "B", "C"] }` → у шаблоні робиться select,
     а бекенд перевіряє, що `value` входить у список;
   - `{ "type": "text", "pattern": "^[0-9]{4}$" }` → перевірка за regex;
   - `{ "type": "bool" }` → як зараз, довіряє `ok`.
   Це вимагає невеликої зміни `_evaluate()` (розпізнавати `type`) і, за бажанням,
   рендера відповідного поля в шаблоні `measurement`.
3. **Тип значення тримати в одному місці.** Щоб уникнути розбіжності «шаблон каже
   число, а допуски описують вибір», найкраще задавати тип у `templates.json`
   (параметр `value_type`) і дублювати/перевіряти його в `limits`. Мінімально — хоча б
   показувати підказку в адмінці, що ключ і тип мають збігатися.

### Підсумок по пункту
Повзунки та дружні поля — це зміна **тільки адмінки** (форма моделі + можливо
`templates.json`). Підтримка нецифрових типів із перевіркою — невелика зміна
`_evaluate()` + схема `limits`.

## 4. SSL-сертифікат і вебкамера

### Чому взагалі SSL
Вебкамера в браузері — це `navigator.mediaDevices.getUserMedia(...)`. Браузери
дозволяють її **тільки на secure context**: HTTPS або `http://localhost`. Зараз
застосунок працює на чистому HTTP:80 (`nginx/default.conf`, `docker-compose.yml`),
тому на робочому місці камера просто не стартує. Отже — так, SSL потрібен.

### Self-signed vs Let's Encrypt
| | Самопідписаний | Let's Encrypt |
| :--- | :--- | :--- |
| Що треба | згенерувати сертифікат самому | публічний домен + DNS, що вказує на сервер |
| «Танці з бубном» | середні: на кожному ПК-клієнті встановити кореневий сертифікат у «довірені», інакше браузер показуватиме попередження | перший запуск certbot (2 команди), далі авто-оновлення cron |
| Для внутрішньої мережі без домену | **підходить** | **не підходить** (немає як підтвердити домен через HTTP-01; DNS-01 потребує керування DNS) |
| Оновлення | вручну (раз на рік) | автоматично |

**Рекомендація:**
- Є публічний домен і DNS → **Let's Encrypt (certbot)**. Мінімум ручної роботи після
  першого налаштування, сертифікат довіряють усі браузери «з коробки».
- Тільки внутрішня мережа, домену немає → **самопідписаний кореневий CA +
  сертифікат сервера**, а кореневий CA один раз встановити на клієнтські ПК
  (це прибирає всі попередження і вмикає камеру). Для зручної генерації можна
  скористатися `mkcert` (створює локальний CA і сертифікат однією командою).

### Що змінити в конфігурації
1. **nginx** (`nginx/default.conf`) — додати `listen 443 ssl` + redirect 80→443:

```nginx
server {
    listen 80;
    server_name _;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name _;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    # ... решта конфіга без змін: root, /api/ proxy, /uploads/, etc.
}
```

2. **docker-compose.yml** — відкрити порт 443 і змонтувати сертифікати:

```yaml
  nginx:
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./certs:/etc/nginx/certs:ro      # сюди кладемо fullchain.pem + privkey.pem
      - ./frontend:/usr/share/nginx/html:ro
      - ./uploads:/uploads:ro
```

3. Покласти сертифікати в новий каталог `./certs/` (або куди пише certbot).

### Новий шаблон «камера» (сама вебкамера)
Додати третій варіант фіксації — `camera` (поряд із `photo`):
- `frontend/templates/camera.html` — `<video>` (превʼю) + кнопка «Зняти».
- `frontend/templates/camera.js`:
  1. `navigator.mediaDevices.getUserMedia({ video: true })` → потік у `<video>`.
  2. Кнопка малює кадр у `<canvas>` і через `canvas.toBlob(...)` отримує JPEG.
  3. Формує `FormData` (`workstation`, `barcode`, `file`) і шле на вже наявний
     `POST /api/measurements/photo` — бекенд для цього вже готовий, нічого міняти не треба.
- Додати запис у `frontend/templates/templates.json` (`"camera": { "title": "Фото з камери", ... }`).

Зауваження: в адмін-превʼю (`?preview=1` у iframe) камера не працює (iframe `inert`
+ політика дозволів) — це нормально, камера потрібна лише на реальному робочому місці.
Якщо камера знадобиться і в превʼю, доведеться дозволити `allow="camera"` на iframe
та зняти `inert`, але це вже окреме завдання.

## 5. Вікно моніторингу (цеховий екран)

### Вимога з Task.md
По центру — годинник великими цифрами; нижче — план/факт; вгорі ліворуч — чекбокс
«показувати план/факт» і вибір теми. Екран у цеху: більшу частину займає час,
трішки — план/факт.

### Рішення (переробка `frontend/monitor/`)
Зараз `monitor/index.html` + `monitor.js` + `monitor.css` малюють шапку з планом,
картки по місцях і качечку. Потрібно:

1. **Гігантський годинник по центру.** Окремий блок `<div class="clock-big">` з
   `font-size` у `clamp(6rem, 20vw, 18rem)` і `tabular-nums`. Використати наявний
   `startClock()` або свій `setInterval`, що виводить `HH:MM:SS` (`uk-UA`).
2. **План/факт одним рядком під годинником.** Напр.: `План 100 · Факт 87 · 87%`.
   Дані з наявного `GET /api/monitor/summary` (після пункту 1 — уже по партіях).
   Якщо партій кілька — по одному рядку на партію.
3. **Чекбокс зверху-ліворуч** «Показувати план/факт» — ховає/показує цей рядок.
   Стан зберігати в `localStorage` (ключ, напр. `monitor.showPlan`), щоб після
   перезавантаження лишалось як було.
4. **Вибір теми** зверху-ліворуч (поруч із чекбоксом): `світла / темна / висока
   контрастність`. Це просто перемикання CSS-класу на `<body>` + збереження вибору в
   `localStorage`. Тему задати через CSS-змінні, які вже є в `shared/style.css`
   (`--card`, `--accent`, `--ok`, `--muted`), тож достатньо перевизначити їх для
   `body.monitor.dark`.
5. **Картки по місцях** — залишити, але зробити їх компактними/згорнутими (опційно
   згортати в один рядок внизу), бо головне тепер час. Качечку можна залишити як є.

Все це — зміни лише у `frontend/monitor/*` (html/css/js), бекенд не чіпаємо
(хіба що `summary` уже змінено за пунктом 1).

## 6. Перегляд по скануванню (плитки)

### Вимога
Окрема вкладка: скануєш штрихкод → система показує **все**, що знає: фото,
параметри (з JSON, але не «сирим» текстом, а гарними плитками).

### Що вже є
`GET /api/units/{barcode}` (`routers/public.py::unit_info`) вже повертає:
`barcode`, `q_tests_data`, `stage_times`, `notes`, `photo_path`, `release_date`,
`product_name`, `article`. Тобто **бекенд готовий**, бракує тільки UI.
Заодно це закриває борг TD-6 «фото без UI перегляду».

### Рішення: нова сторінка `/unit/`
1. Створити `frontend/unit/index.html` + `unit.js` + (опційно) `unit.css`.
   Nginx уже роздає директорії через `try_files $uri $uri/`, тож `/unit/` сама
   відкриє `unit/index.html` — конфіг не міняємо.
2. На сторінці — поле сканування (штрихкод + Enter, як в інших шаблонах).
   При скануванні → `GET /api/units/{barcode}`.
3. **Рендер плитками:**
   - плитка «Продукт»: назва + артикул + дата випуску;
   - плитка «Фото»: `<img src=photo_path>` (якщо є), інакше «фото немає»;
   - по одній плитці на кожен ключ `q_tests_data`: назва ключа, значення, бейдж
     «в нормі» / «поза допуском» (за `ok`), номер місця;
   - плитка «Етапи» (`stage_times`): список `ws<N>` → час у вигляді таймлайну;
   - плитка «Примітки» (`notes`).
4. Додати посилання на `/unit/` у шапках (поруч із «Моніторинг»/«Адміністрування»,
   у `index.html` і `monitor/index.html`).

Це повністю фронтендова задача: жодних змін у бекенді не потрібно (хіба що, якщо
хочеться, додати в `unit_info` розгорнуті назви робочих місць замість `ws<N>` —
тоді маленький JOIN у `public.py`).

## Підсумок: рекомендований порядок робіт

Згруповано за «в першу чергу» (пріоритети замовника) і за вартістю:

| # | Задача | Де зміни | Складність | Примітка |
| :-- | :--- | :--- | :--- | :--- |
| 1 | Партії (план/факт) | БД + backend + admin + monitor | ⭐⭐⭐ | обговорити семантику «факт» (розділ 1) |
| 2 | Форма робочого місця + підказки | фронтенд admin | ⭐ | швидка перемога |
| 3 | Допуски повзунками + типи | фронтенд admin (+ трохи `_evaluate`) | ⭐⭐ | без міграцій, якщо без `type` |
| 4 | SSL + вебкамера | nginx + compose + новий шаблон | ⭐⭐ | залежить від «домен чи LAN» |
| 5 | Моніторинг-годинник | фронтенд monitor | ⭐ | |
| 6 | Перегляд по скануванню | новий фронтенд `/unit/` | ⭐ | бекенд уже готовий |

**Найбільша невизначеність** — пункт 1 (що таке «факт» партії і чи кілька партій
одночасно). Це варто узгодити перед кодуванням; решта пунктів можна робити
паралельно і незалежно.
